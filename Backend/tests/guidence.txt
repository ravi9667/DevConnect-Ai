1. WHAT IS DEVCONNECT AI?
================================================================================

DevConnect AI is a developer collaboration platform.

The main purpose of this application is to provide developers a single
platform where they can:

- Create a professional developer profile
- Discover other developers based on their skills
- Create projects
- Join other projects
- Build teams
- Collaborate with other developers
- Communicate with team members
- Get AI-powered developer/project recommendations
- Get AI assistance during development

Simple definition:

"DevConnect AI is a developer collaboration platform where developers can
create professional profiles, discover other developers based on their
skills, create and join projects, form teams, communicate with collaborators,
and use AI-powered features to find better project and developer matches and
get development assistance."

The backend is responsible for handling:

- Authentication
- Users
- Projects
- Teams
- Collaboration
- Messages
- Notifications
- AI features
- Security
- Database
- APIs

2. BACKEND DEVELOPMENT APPROACH
================================================================================

We are not putting all the code inside one file.

The backend follows a layered and modular architecture.

Basic request flow:

Client / Frontend
       |
       v
     Route
       |
       v
   Middleware
       |
       v
   Controller
       |
       v
    Service
       |
       v
     Model
       |
       v
   MongoDB


Meaning:

Route:
Determines which API endpoint should handle the request.

Middleware:
Runs between request and controller.
Used for validation, authentication, error handling, etc.

Controller:
Receives the request and decides what operation needs to happen.

Service:
Contains reusable business logic.

Model:
Defines the structure of data stored in MongoDB.

Database:
Stores the actual application data.

--------------------------------------------------------------------------------
6.2 PASSWORD HASHING
--------------------------------------------------------------------------------

Inside user.model.js we use Mongoose pre-save middleware.

Example:

userSchema.pre("save", async function(next) {

    if (!this.isModified("password")) {
        return next();
    }

    this.password = await bcrypt.hash(this.password, 12);

    next();
});


Meaning:

When user is saved:

Plain password
      |
      v
bcrypt
      |
      v
Hashed password
      |
      v
MongoDB


Why?

If the database is compromised, the attacker should not directly get the
user's original password.


--------------------------------------------------------------------------------
6.3 PASSWORD COMPARISON
--------------------------------------------------------------------------------

We also have:

userSchema.methods.isPasswordCorrect = async function(password) {
    return await bcrypt.compare(password, this.password);
};


During login:

User enters password
       |
       v
bcrypt.compare()
       |
       v
Stored password hash
       |
       v
true / false


IMPORTANT:

We do NOT decrypt the password hash.

bcrypt is used to compare the entered password against the stored hash.

9. REFRESH TOKEN MODEL
================================================================================

File:

src/models/refreshToken.model.js


Purpose:

Refresh tokens represent user sessions.

We keep refresh tokens in a separate collection.


Why?

Because one user can be logged in from multiple devices.


Example:

User Ravi:

Laptop
Mobile
Chrome
Another browser


Each can have its own session.


Concept:

users
   |
   |---- refreshtokens
           |
           |---- Laptop session
           |---- Mobile session
           |---- Browser session


The refresh token document contains information such as:

- user
- hashed refresh token
- device information
- IP address
- browser
- operating system
- expiry time
- last used time


This allows us to later implement:

- View logged-in devices
- Logout one device
- Logout all devices
- Session management
- Refresh token rotation


IMPORTANT:

The refresh token is hashed before being stored in the database.

We should NEVER store the raw refresh token directly in MongoDB.

13.4 requestInfo.js
--------------------------------------------------------------------------------

Purpose:

Extract information from the incoming request.

We use UA Parser to get information from the User-Agent header.


Example:

import { UAParser } from "ua-parser-js";

export const getRequestInfo = (req) => {

    const parser =
        new UAParser(req.headers["user-agent"]);

    const result =
        parser.getResult();

    return {
        ip: req.ip,
        browser: result.browser.name,
        os: result.os.name,
        device: result.device.type || "Desktop",
    };
};


Important:

parser is NOT the device itself.

parser is an object that reads and analyzes the User-Agent string.

Example User-Agent:

"Mozilla/5.0 ... Chrome ... Windows"


UAParser analyzes this and gives:

browser
os
device


We then create our own clean requestInfo object.

23. LOGIN OTP VERIFICATION
================================================================================

Current controller logic:

export const verifyLoginOtp = asyncHandler(async (req, res) => {

    const { email, otp } = req.body;

    const user = await User.findOne({ email });

    if (!user) {
        throw new ApiError(404, "User not found");
    }

    const loginOtp = await LoginOtp.findOne({
        user: user._id,
    }).select("+otp");

    if (!loginOtp) {
        throw new ApiError(400, "OTP not found");
    }

    if (loginOtp.expiresAt < new Date()) {

        await LoginOtp.deleteOne({
            _id: loginOtp._id,
        });

        throw new ApiError(
            400,
            "OTP has expired"
        );
    }

    const isOtpCorrect =
        await bcrypt.compare(
            otp,
            loginOtp.otp
        );

    if (!isOtpCorrect) {

        loginOtp.attempts += 1;

        await loginOtp.save();

        throw new ApiError(
            400,
            "Invalid OTP"
        );
    }

    // JWT + session handling comes here

});


IMPORTANT:

OTP is hashed in database.

So we don't compare:

otp === databaseOtp

We use:

bcrypt.compare(
    enteredOtp,
    storedOtpHash
);

25. HTTP ONLY COOKIES
================================================================================

We decided that JWTs should be stored in HttpOnly cookies.

NOT localStorage.

Example concept:

res.cookie(
    "accessToken",
    accessToken,
    accessCookieOptions
);


And:

res.cookie(
    "refreshToken",
    refreshToken,
    refreshCookieOptions
);


HttpOnly means JavaScript running in the browser cannot directly read the
cookie.

The browser automatically sends the cookie with requests when cookie
conditions are satisfied.

31. IMPORTANT DEVELOPMENT RULES
================================================================================

1. Do not put everything in controllers.

2. Reusable business logic should go into services.

3. Database structure should remain inside models.

4. API endpoints should remain inside routes.

5. Common request processing should go into middleware.

6. Temporary authentication data should not unnecessarily be stored inside
   the User model.

7. Secrets should always remain inside environment variables.

8. Never store plain passwords.

9. Never store raw refresh tokens in the database.

10. Do not expose JWT tokens unnecessarily in API response bodies when using
    HttpOnly cookies.

11. Validate incoming request data before processing it.

12. Use proper HTTP status codes.

13. Keep API responses consistent.

14. Do not blindly add technologies just because they are "production"
    technologies.

15. Every technology should solve an actual problem.
